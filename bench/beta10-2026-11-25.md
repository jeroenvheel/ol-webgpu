# Memory and speed of 0.1.0-beta.10 (2026-11-25)

`npm run test:memory`, `npm run bench -- --layers=webgl2,webgpu` (twice) and
`npm run test:memory -- --big` on `main` at `ed5bc08` (0.1.0-beta.10). AMD
Radeon R9 200 Series, D3D11, Playwright Chromium. One after the other, with
about 11 GB of 16 GB free before each run.

## Memory

Each scenario runs with `ol/Feature` and with RenderFeatures, on both
backends: 12 cycles after 3 to warm up.

- 0 checks failed. After disposing everything 0 features, RenderFeatures,
  maps, layers, renderers, canvases and buffers are left in all four passes;
  the heap is 11.9–12.6 MB against 7.7 MB for the empty page.
- Heap growth per cycle is 0–9 KB, except making and disposing a whole map
  (40–43 KB) and labels with new texts (27–32 KB, ol's table of strings).
  Both as with beta.6 (35–38 KB and 21–28 KB).
- The two scenarios that are new since beta.6 grow by 1–2 KB per cycle: a
  layer that is removed and not disposed (`dropLayer`) and a map that is
  dropped without disposing its layers (`dropMap`).
- The number of live buffers, textures, programs and vertex arrays does not
  change in any scenario.

### A big layer

300k points, 200k lines, 50k polygons, against 21 November
([memory-2026-11-21.md](memory-2026-11-21.md)):

| | WebGL2 | WebGPU |
|---|---|---|
| the features themselves, heap | 610 MB (was 609) | 610 MB (was 609) |
| added by the layer, heap | 518 MB (was 528) | 354 MB (was 364) |
| the same with RenderFeatures | 175 MB + 407 MB | 175 MB + 243 MB |
| a rebuild | 0.6–0.7 s | 0.6 s |

The heap does not grow over four rebuilds (0.1 MB each) and is back at
8.6–9.0 MB after everything is dropped.

## Speed

before beta.8. Milliseconds, lower is better.

- Nothing changed beyond the variation between runs. Time to first render
  is 3–5% shorter for lines and polygons; for points one of the two WebGL2
  runs is 14% longer and the other the same.
- Frame times for polygons are 0.5–1 ms higher on WebGPU in both runs. That
  is within what sessions differed by before, but it is the one number that
  moved the same way twice.
- Picks and the worker stages are unchanged (the Rust sources did not
  change).

An earlier run of the same evening
(`results-2026-11-25T19-12-03-803Z.json`) was made while the machine was
short on memory and is not used here: its ready times were 9–32% longer for
points and 5–7% for lines, and the worker stages were slower too.
