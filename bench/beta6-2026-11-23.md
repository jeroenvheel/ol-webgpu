# Memory and speed of 0.1.0-beta.6 (2026-11-23)

`npm run test:memory` and `npm run bench -- --layers=webgl2,webgpu` on `main`
at `2ea178c` (0.1.0-beta.6). AMD Radeon R9 200 Series, D3D11, Playwright
Chromium.

## Memory

Each scenario runs with `ol/Feature` and with RenderFeatures, on both
backends: 12 cycles after 3 to warm up.

- 0 checks failed. After disposing everything 0 features, RenderFeatures,
  maps, layers, renderers, canvases and buffers are left in all four passes;
  the heap is 11–12 MB against 7.3 MB for the empty page.
- Heap growth per cycle is 0–6 KB, except making and disposing a whole map
  (35–38 KB) and labels with new texts (21–28 KB, ol's table of strings, see
  [memory-2026-11-21.md](memory-2026-11-21.md)). Both as before.
- The number of live buffers, textures, programs and vertex arrays does not
  change in any scenario.
- With RenderFeatures the scenarios that keep a layer have a heap of about
  25 MB (WebGL2) and 22 MB (WebGPU), against 38 MB and 35 MB with
  `ol/Feature`.

The first run reported 15 failed checks. All were errors of the Vite dev
server ("Outdated Optimize Dep", its dependency cache being refreshed after
the sources changed) and every scenario was "ok"; the second run was clean.
The same happened on 21 November after switching versions.

## Speed

Two runs of beta.6, against the two runs of beta.5 of 21 November
([memory-2026-11-21.md](memory-2026-11-21.md)). Milliseconds, lower is better.

- Time to first render is about 21% shorter for points on WebGL2, 16% on
  WebGPU, 9–11% for lines and 8% for polygons.
- Frame times are 0.2–0.5 ms higher for lines and polygons in these runs,
  which is at the edge of the variation between runs.
- Picks and the worker stages are unchanged (the Rust sources did not
  change).
- `pickReady`, the wait until data-driven sizes are measured, is 20–40 ms
  for points and lines in every run; before it was either about 0 or
  150–270 ms.

The beta.5 runs are of another session, two days earlier, not measured
alternately with beta.6. Sessions differed by up to 14% in a single run
before, so the small differences (frame times) are not reliable; the shorter
ready times are larger than that and the same in both runs.
