# Memory investigation (2026-11-21)

What the layers keep in memory, whether anything leaks, and what was changed.
Measured on `main` after 0.1.0-beta.4, AMD Radeon R9 200 Series, D3D11,
Playwright Chromium. `npm run test:memory` repeats the leak checks.

## Method

`test/rendering/memory.ts` has scenarios that repeat one thing a layer does:
a map is made and disposed, a layer is swapped, the view moves (the buffers
are built again), the style or a style variable changes, features come and
go, labels are laid out again, labels with new texts, picks. The runner
measures after a garbage collection, before and after the repetitions:

- the JS heap (which includes array buffers);
- the WebGL and WebGPU objects that are alive, counted by wrapping what
  creates and deletes them;
- the wasm memory of the main thread;
- the instances of `Feature`, `Map` and the layer class that are still alive
  after everything is disposed;
- on Windows, the private memory of the browser's renderer and GPU process.

A big layer (300k points, 200k lines, 50k polygons) was measured step by
step for the numbers in megabytes.

## Found and fixed

**Hit detection with more than one layer was wrong.** All layers shared one
hit index in the main thread's wasm instance, so every layer was picked in
the index of the layer that was built last. In a map with two layers, a
click on a feature of the first one found nothing, and a click on the second
also returned a feature of the first. Each layer now has its own index, freed
when the layer is rebuilt or disposed. The picking test has a second layer.

**The GPU process grew with every rebuild.** New GPU buffers were made for
every rebuild and the old ones deleted, but the driver gives that memory back
late. With the big layer:

| | before | after |
|---|---|---|
| layer drawn | 518 MB | 518 MB |
| after 4 rebuilds | 1806 MB | 518 MB |
| after 8 rebuilds | 2797 MB | 518 MB |

The buffers of the previous build are now written again when they are large
enough (not more than twice too large), on both backends. ol's own layer
shows the same growth, to about 1.2 GB with this data.

**The last map stayed alive after it was disposed.** The canvas grouping
kept the frame state of the last rendered frame, and through it the map, its
layers and all features. After disposing everything the heap was 32 MB
instead of 11 MB in the test, and with the big layer it would be all of its
features. It is a `WeakMap` now.

**The worker kept the memory of its largest build.** wasm memory only
grows. After the big layer was built the worker's instance held 329 MB for
as long as the page lived. The worker now replaces a large instance (over
32 MB) by a new one when no build came for five seconds; measured 1 MB
afterwards. The same on the main thread when the last layer with a large
index is disposed. The built index is also dropped as soon as it is read,
before the buffers are tessellated.

**WebGPU kept a second copy of all buffers.** Both backends kept the
vertex, index and instance data in memory to upload it again after a context
or device loss. On WebGPU that copy is gone (164 MB of 1137 MB heap with the
big layer): after a lost device the buffers are built again instead. WebGL2
keeps the copy, because there a layer also needs it when it moves to another
canvas (when layers are added or removed between), and building again would
show as a blank layer for a moment.

**Measured texts were kept without limit.** The advance widths of whole
label texts are cached per font. Labels that keep changing (times, counts)
grew that cache by about 117 KB per 400 new labels. The caches are now
emptied at the start of a layout when a font has more than 20000 texts.

**Smaller things.** The canvas of a disposed surface gives its backing
store back at once (size set to zero). The atlas texture of a WebGL context
is deleted with the last layer of that context. A map of pacing data per map
id is bounded.

## Result of the leak checks

All scenarios, 12 cycles each after 3 to warm up, both backends:

- heap growth per cycle is 0–6 KB, except making and disposing a whole map
  (about 35 KB per cycle over 12 cycles, 8 KB per cycle over 60: it levels
  off) and labels with new texts (about 25 KB per cycle, bounded as above);
- the number of live buffers, textures, programs, vertex arrays and
  framebuffers does not change in any scenario;
- after disposing everything: 0 features, 0 maps, 0 layers, 0 renderers,
  0 canvases and 0 buffers are left; the heap is 11 MB against 7 MB for the
  empty page.

## What a big layer costs

300k points, 200k lines, 50k polygons, after the changes:

| | WebGL2 | WebGPU |
|---|---|---|
| the features themselves (ol, before any layer) | 609 MB heap | 609 MB heap |
| added by the layer, heap | 528 MB | 364 MB |
| GPU process | 518 MB | 470–600 MB, 295 MB when idle |
| worker wasm while building / idle | 329 MB / 1 MB | 329 MB / 1 MB |

Most of what the layer adds on the heap is ol's `MixedGeometryBatch`, the
flat copy of all geometries that ol's instruction generators read, plus on
WebGL2 the second copy of the buffers.

## Not changed

- **`MixedGeometryBatch`** is the largest part of the layer's own memory. It
  is ol's structure and is needed to build the instructions.
- **The WebGL2 copy of the buffers** (see above). It could become an option.
- **The process memory after everything is disposed** stays well above the
  empty page (about 1.2–1.4 GB after the big layer, with a heap of 8 MB).
  The heap and the wasm memory are gone by then; what remains is memory the
  browser's allocators have not returned to the system, which cannot be
  influenced from the page.
- **The glyph atlas** is a canvas of 2048 by 512 to 4096 pixels, shared by
  all layers, plus one texture per WebGL context or per device.

## A mistake in the test itself

The first runs lost their WebGL context after a few seconds. That was the
test's style: it read a property the synthetic lines do not have, which gave
line widths that made one frame take over two seconds of GPU time, and the
driver reset the device. ol's layer was as slow with that style. With the
right property no context is lost.

No change beyond the variation between runs in frame time, pick time and
time to first render. Two small differences repeat in every run:

- lines are ready about 2% later on both backends (about 20 ms);
- an index query takes about 0.0005 ms longer for lines and polygons: the
  index of the layer is looked up by its handle. It does not show in the
  pick times measured in the browser.

Two runs of beta.5 made before this comparison, in another state of the
machine, gave ready times of up to 991 ms for points on WebGL2 and 986 ms
for lines on WebGPU; a single run varies by that much, which is why the
versions were measured alternately.

The JavaScript fallback tessellation of lines measured about 1000 ms on
beta.5 against about 1530 ms on beta.4. The changes do not touch that code
and the difference is not explained.

The benchmark does not time a rebuild after a pan, which is where the reuse
of GPU buffers acts.

## Labels with new texts, more cycles

Only the scenario `labelsNewText` (400 labels with texts never drawn
before, per cycle), with more cycles than the 12 of the test.

The memory of the processes levels off:

| Cycles | WebGL2 GPU process | WebGPU GPU process |
|---|---|---|
| 36 | 96 → 267 MB | 329 → 409 MB |
| 100 | 97 → 262 MB | 334 → 338 MB |
| 300 | 97 → 217 MB | 341 → 251 MB |

The renderer process went from 77 to 260 MB in 100 cycles and from 74 to
280 MB in 300.

The heap does not level off. Sampled every 10 cycles over 800 cycles it
went from 10.6 to 28.1 MB on WebGL2 and from 10.7 to 28.3 MB on WebGPU:
about 26 KB per cycle, 65 bytes per new text.

That is a table of ol, `stringToFloatMap` in `ol/expr/gpu.js`. Every string
that a style reads from a feature gets a number for the shaders, and no
string is ever forgotten. After 150 cycles it had 60002 entries, for the
60000 texts made, and the same 60002 with ol's own `WebGLVector` layer in
the same test. The cache of measured texts of this package had 19415
entries then, under its limit of 20000.

It matters only where label texts, or other string properties a style
reads, keep getting values that were never seen before (times, counts):
about 6.5 MB per 100000 different strings. A fixed set of names is paid for
once.

Not changed. With labels drawn on the GPU (the default) the `text-*`
properties do not have to go through ol's shader builder. Leaving them out
there would end this growth for labels and save one number per vertex for
each property a label reads. It would not help for other string properties
or for `text: 'canvas'`, which needs those attributes.
